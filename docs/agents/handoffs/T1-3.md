## 1. Completed work

### F3 — the same defect, reintroduced by the fix for the last one

Worth stating plainly because it is the most useful thing in this round. `transcript[].disclosed`
was added in commit `4b2185d` — **the same commit that fixed the identical bypass on the agent
envelope.** A `free_busy` entry accepted a `full` availability payload labelled `therapy`, and
`disclosed.summary` accepted `"Ana has therapy at 2pm"` at any level, because it was
`type: string`.

The lesson the first fix should have taught, and did not: **the ladder travels with the payload,
not with one of its carriers.** Adding a new carrier is adding a new bypass unless the
conditionals come with it. Three changes follow from that:

- Per-carrier conditionals on `transcript.items`, mirroring the envelope's.
- `summary` is gone. Entries carry `summary_code` from a closed vocabulary and the UI renders a
  sentence from it plus the structured data already present. Free prose next to a disclosure
  level is the `reason_code` lesson again: `"Ana has therapy at 2pm"` is 22 characters and
  validates against `type: string` at every rung of the ladder.
- **`scripts/ci/check_disclosure_matrix.py`** (on `main`) now sweeps every carrier exhaustively
  and fails when a schema grows a third availability reference it does not know about. A review
  caught this; a review is not a control.

### F1 — a normal state was unrepresentable, and the workaround was a leak

The rule required a non-empty `pending_approvals` whenever `status` was `awaiting_approval`. But
that array is viewer-private. Once Ana approves and Ben has not, the negotiation is still
`awaiting_approval` and Ana's array is correctly empty — so her own client could not render the
response her approval had just produced. The only two ways to satisfy the schema were to
fabricate a pending decision or to show her Ben's. **A schema bug whose least-effort workaround
is a privacy breach is worse than a schema bug.**

`viewer.awaiting_me` now carries that question, enforced in both directions so the flag cannot
drift from the array it describes. New fixture `valid-awaiting-approval-viewer-done.json` is
exactly the state that used to be rejected.

### F2 — channel consent could not be completed from the published API

Registration bound to no negotiation, and nothing raised the `post_to_channel` approvals the
state schema already described. Four steps now, each answering a different question:

| Step | Call | Question | Authenticated as |
|---|---|---|---|
| 1 | `POST /channels` | Is this a real channel with our bot in it? | the bot |
| 2 | `POST /channels/{id}/members` | Which student is which Discord user? | **the student** |
| 3 | `POST /negotiations/{id}/channel-bindings` | May *this* negotiation be discussed in *that* room? | a participant |
| 4 | `GET .../channel-summary` | — serves only once `confirmed` | the bot |

Step 2 is the student's and never the bot's: if the bot could assert the identity mapping, every
consent decision after it would be worthless. Step 3 raises an ordinary `post_to_channel`
approval per participant, so Track 3 adds no second consent mechanism. Consent is per
negotiation; every participant approves including non-members (posting reveals they are in it
either way); room growth forces re-consent; one withdrawal ends it for everyone.

The 403 deliberately does not distinguish declined from pending — a bot that could tell them
apart would be a way to report somebody's private no into the room.

### F5 — a stream two teams could implement incompatibly

## 5. Known limitations

- **Nothing here runs.** The schemas are a second net; the primary guarantee is the server-side
  egress filter and it does not exist until T2. No runtime privacy claim has been tested.
- **`channel-summary.text` is free prose composed server-side and no schema can check it.** It
  is the one sentence that reaches a group chat. It rests entirely on T2's care; the `free_busy`
  ceiling bounds what it has to work with. Flagged in T2's assignment as privacy-critical.
- **Channel consent is to an audience size, not a membership list.** A room that swaps one
  member for another keeps the same count and does not trigger re-consent. Growth is caught;
  substitution is not.
- `state_version` atomicity under concurrent approvals is specified, not implemented. T2's.
- The matrix catches an unswept *availability* carrier. A future contract that carries some
  other disclosure-levelled payload would need its own registration.
- No `tests/` directory exists yet, so there is no integration suite to regress.

## 6. Decisions and assumptions

- **`summary` removed rather than length-limited or filtered.** A shorter string is still a
  string. The closed vocabulary is the only version a schema can actually enforce.
- **Every participant approves a channel post, including non-members.** Posting reveals they are
  in the negotiation whether or not they can read the room.
- **One withdrawal ends the binding for everyone.** An audience cannot be partially un-told.
- **Re-consent triggers on audience growth only.** Tracking a full membership list would mean
  storing Discord rosters, which is more data about more people.
- **`viewer.awaiting_me` rather than deriving it from `pending_approvals`.** Explicit, so a
  filtered view that gets one wrong fails validation instead of rendering a wrong prompt.
