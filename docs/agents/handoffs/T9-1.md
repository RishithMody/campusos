## 1. Completed work

A Discord bot registers the actual invoking guild text channel and responds to `/schedule`
with ephemeral setup instructions. `/watch` polls the consent-gated summary endpoint for up
to 90 checks, ten seconds apart, and posts only literal contract templates. Every update
requires a fresh successful API response; duplicate text is suppressed within a watcher.
Denials, malformed summaries and outages stop it without disclosing negotiation information.
No participant state, human token or model client enters the bot.

The separate student terminal companion supports account/contact lookup, creation, linking,
scoped grants, availability, channel binding, private state/binding reads, decisions and
withdrawal. Decisions show the exact current disclosure preview, proposed slot when present,
and version, then require the student to type approve or decline. No stale approval retry.

The integration tests use T2's real FastAPI/LangGraph/privacy/persistence code with mock
inference, SQLite, fakeredis and fake Discord. Three conflicting free intervals yield a
proposal; two approvals create zero commitments and the third creates three. A no-overlap
case escalates. Pending/declined/withdrawn/grown audiences cannot produce channel posts.

## 5. Known limitations

- T9 is ready for review, not fully live-accepted. No actual Discord account/server was touched.
- Student actions require a terminal and private JSON files. T5's browser UI is queued; no
  working app links or OAuth callbacks are invented. Operator identity provisioning and
  verified Discord OAuth linkage remain T2's existing bootstrap process.
- The assignment says bots poll channel-bindings. T2's GET implementation calls participant
  authorization and refuses bot credentials. Student CLI can read it. Bot uses the summary
  endpoint's authoritative gate instead. This is a documented integration deviation.
- Frozen summaries expose timestamps only after convergence. Proposed time and disclosure
  preview are visible privately in the student terminal before approval, not in the room.
- Audience growth stops the watcher, raises approvals in T2, and requires `/watch` after
  re-consent. Same-size audience substitution is not detected by the frozen backend design.
- Already-posted messages remain. Authorization and Discord send are separate operations:
  withdrawal during an in-flight delivery cannot atomically prevent that send. No delivery
  lease exists in the frozen API. Discord transport may wait on rate limits.
- Watchers last 15 minutes, one per room, and are not persisted across restart. Repeat `/watch`
  may repeat the last authorized summary. No cached response is retried after an API error.
- No external Calendar writes: T2 records local commitments only.
- Python 3.11 is the tested runtime; discord.py emits the audioop deprecation warning above.
- Independent review has not run; do not treat the T1 waiver as covering T9.

## 6. Decisions and assumptions

Followed the frozen API and updated T9 assignment over stale architecture prose referring to
`channel-summary.text`. Renderer validates directly against the local OpenAPI ChannelSummary,
including additionalProperties rejection, and adds timestamp/status consistency checks.
The literal template map is the only public text path; consent_withdrawn exists in the contract
map but is never broadcast because withdrawal must be indistinguishable from other denials.

Discord.py is a transport library, not a new application framework. No new negotiation runtime,
web framework, inference dependency or backend ownership introduced. The README cites the
Discord official setup and discord.py interaction docs consulted during implementation.
