## What is still NOT verified, and why

**1. Guild member enumeration — the privileged intent is off.**
`GET /applications/@me` returns `flags=0`: `GATEWAY_GUILD_MEMBERS` (`1 << 16`) is not
set, so `GET /guilds/{id}/members` answers `403 Missing Access`. Production
`audience()` therefore cannot run at all against this application, and the demo supplied
the member list instead (`scripts/demo/server.py`). **Nothing here is evidence about
`audience()`'s pagination, deduplication, or incomplete-page handling.** Those remain
mock-tested only.

Fix: developer portal → CampusOS → Bot → Privileged Gateway Intents → Server Members
Intent → on. Then delete `scripts/demo/server.py` and run `backend.app:create_app`.

**2. `can_view` was exercised on an easy guild.** Two members, zero channel overwrites,
no administrator, no role-level or member-level overwrite. The branches that actually
worried us — `@everyone` channel overwrite, role overwrite aggregation, member overwrite
last, administrator short-circuit — are still pinned only by fixtures their own author
wrote. A guild with a private channel and a couple of roles would settle it.

**3. The same-size membership swap could not be staged.** Only one real human account
exists in the test guild, so the T12 case was demonstrated as a *shrink* live (audience
changed → re-consent) and remains fixture-tested for the same-size case.

**4. The OAuth link ceremony was bypassed.** `backend.manage link-discord` requires the
student's Discord OAuth access token, which we do not have. The demo student's
`discord_id` was written directly by the operator, taken from the guild's `owner_id`.
No product code was changed and no check was weakened — but the *binding between a
CampusOS subject and a Discord identity was asserted, not proved*, which is exactly the
boundary `docs/agents/status.md` has been flagging.

**5. Not tested:** rate limiting, a long `/watch` run, PostgreSQL or Redis killed
mid-negotiation **while Discord was live**, or a second concurrent watcher.

## Three defects found

1. **`CAMPUSOS_DISCORD_TOKEN` in `.env` was an 18-character placeholder**, not the bot
   token. The backend verifies channel audiences with it, so every binding would have
   failed closed with no indication that the cause was configuration. Set to the real
   bot token (`.env` is gitignored; previous value backed up to `.env.backup-t12`).
2. **A missing privileged intent surfaced as `Problem(403)`, not `Problem(503)`** —
   `DiscordREST.fetch` mapped *any* non-200 to `403`, so a configuration failure read as
   an authorization refusal. Reported rather than changed for the intent case, because
   Discord's own answer there (`403 Missing Access`) genuinely is about authority. The
   adjacent case was not benign — see finding 3.

3. **A Discord rate limit was reported as a consent refusal.** Found by it happening, two
   hours after the first live run, while rehearsing the demo: a staged negotiation with a
   `confirmed` binding and a matching audience fingerprint started answering `403`, and
   the binding was never flipped to `pending_reconsent` — so the refusal came from before
   the audience comparison, not from it.

   `GET /guilds/{id}/members/{user}` carries a bucket of **five per second**, measured
   from `x-ratelimit-remaining`, and each audience check spent **three** of them: one
   inside `context()` and one per roster member, re-fetching the bot's own document that
   `context()` had already proved. Two demo commands in quick succession exhausted it, and
   `fetch` turned the resulting `429` into the same uniform `403` the bot gets when nobody
   consented. Every diagnosis it suggested pointed at the consent model, which was working
   perfectly.

   Confirmed rather than inferred: twelve concurrent member fetches reproduce it, and the
   captured 429 carries `retry_after: 0.973, global: false`.

   Fixed in `fetch`: a `429` or any `5xx` now raises `Problem(503, "Channel verification
   unavailable")` — Discord declining to answer — while `401/403/404` stay `Problem(403)`,
   Discord answering about authority. Both still fail closed; they are no longer the same
   event. `tests/integration/connector/test_discord_failclosed.py` pins the split. The
   demo server also stopped re-fetching the bot's own member document, cutting a third of
   the budget. This does not weaken the uniform-403 consent guarantee: `channel_summary`
   checks the binding status **before** it asks Discord anything, so a `503` can only ever
   follow a binding that was already `confirmed` and never distinguishes `declined` from
   `pending`.
