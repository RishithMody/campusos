## Objective

Build the interface that makes the negotiation legible: what each student is committed to, what
their agent is negotiating, what it has disclosed on their behalf, and what accepting a proposal
will reveal. This is the Track 2 demo surface — a judge watching it should understand both the
outcome *and* the privacy model without being told.

**Every view above is served by a published endpoint — you never invent one.** If something you

| What you render | Where it comes from |
|---|---|
| Dashboard: pending negotiations, items awaiting you | `GET /negotiations` (`awaiting_me` flags the ones that need the student) |
| Commitments | `GET /negotiations?status=converged` → `agreed_slot` |
| What the agent disclosed on the student's behalf | `transcript[].disclosed` in `NegotiationState` — the payload, not just the level |
| Live negotiation visualisation | `GET /negotiations/{id}/stream` (SSE, full filtered state per event) |
| Approval UI, and what accepting reveals | `pending_approvals[].discloses` — render `summary`, `to` and `fields` **before** the approve control |
| Submitting the decision | `POST /approvals/{id}` with the `state_version` you were shown; a 409 means re-read and re-ask |
| Chat with the student's own agent | `POST /me/chat` (SSE) |
| Which participant is the viewer | `viewer.student_ref` — every other id is a per-negotiation pseudonym |

### The disclosure ladder — the specification your privacy tests are written against

| Level | May contain | May never contain |
|---|---|---|
| `none` | a yes/no on one proposed time | any enumeration of busy times |
| `free_busy` | intervals busy / free / tentative | reason, category, label, location, participants |
| `category` | `free_busy` + `academic` \| `work` \| `social` \| `personal` | free text of any kind |
| `full` | `category` + a human-readable label | — needs an explicit, logged, scoped grant |

`"busy 2-4pm"` is permitted at `free_busy`. `"therapy at 2pm"` is only ever possible at `full`.
Default for a new negotiation is `free_busy`. Implement the enum exactly; do not reinterpret it.

**The category enum is deliberately blunt.** `personal` absorbs health, therapy and family. Never
add `medical`, `health` or similar — a category that reveals *why* someone is busy defeats the
ladder. **Reasons are a closed vocabulary** (`reason_code`), never prose: free-text explanation
is the most common way a careful system leaks.

### Decisions already made that you must not relitigate

- **Disclosure is enforced server-side, on egress, in one place** (the privacy service). Not in
  agents, not in clients. A client bug must not become a privacy breach.
- **Identity comes from the validated token, never from a client-supplied id**, on every path.
- **Cross-student reads need an explicit grant row and write an audit record.** No implicit sharing.
- **`student_ref` is a per-negotiation pseudonym**, never a name, email or stable id.
- **No MCP anywhere.** Cubbie's sandbox does not support it. The Skill boundary is HTTPS/443.
- **Agent-to-agent traffic never routes through Cubbie** — Cubbie texts only its own student.
- **The negotiation loop is bounded** (`max_rounds`, ceiling 20). Failure to converge is a
  product outcome that escalates to a human, not an error to retry away.
- **Contracts are frozen.** Need a change? Write it in your handoff, set `REVIEW`, and stop.


### Specific to T5

- **Generate** TypeScript types from `contracts/`; do not hand-write them. A hand-copied type is
  contract drift waiting to happen.
- Render `negotiation-state.schema.json` directly. It is designed as a product surface: statuses
  `failed`, `expired` and `cancelled` are **normal outcomes to show honestly**, not errors to hide.
- The transcript must show **what the student's agent disclosed on their behalf**, at what level.
  That visibility is a product requirement, not a debug view.
- The approval UI must state exactly **what will be revealed if the student accepts**, before
  they accept. Informed consent or it is not consent.
- **Never render a field above the permitted disclosure level, even if the API returns one.**
  There is a required test for this. Defence in depth: the server should never send it, and you
  should never draw it.
- `GET /negotiations/{id}/stream` is server-sent events, each event a full filtered
  `NegotiationState`. Two participants can legitimately receive different documents.
- Two students in one negotiation are in **different trust domains** (boundary B2 in
  `docs/architecture.md`). Never build a view that merges their raw data.
