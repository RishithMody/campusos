## Objective

Build the Track 3 deliverable: an assistant that joins a group chat and coordinates a shared
plan — collecting everyone's availability, proposing a time, and gathering confirmations —
without revealing *why* anyone is busy.

This is the **group-side surface of the same negotiation** Track 2 runs. It reuses
`contracts/availability.schema.json` and the T2 backend. It does not reimplement negotiation,
and it holds no disclosure logic of its own.

## Why Discord, and not Cubbie

Cubbie has no group chat and **cannot text anyone but its own student**
(`docs/hackathon-requirements.md` §6). Track 3 explicitly does not need to be built on Cubbie
and accepts any messaging app. Discord was confirmed by the human (decision D4).

## Acceptance criteria

- [ ] Bot joins a server channel and responds to a scheduling request in that channel
- [ ] Collects each member's availability **without revealing why** anyone is busy
- [ ] Produces a concrete proposed time from conflicting constraints
- [ ] Collective decision flow: members confirm or decline; the decision is recorded
- [ ] Nothing is committed until the required confirmations land
- [ ] Shows what was shared, never more — visibility into agent decisions where permitted
- [ ] Degrades honestly when the backend is down; no private data in any error message
- [ ] Runs against the mock backend with **no GPU**
- [ ] Bot token comes from the environment; no token, secret or credential in Git

### The disclosure ladder — the specification your privacy tests are written against

| Level | May contain | May never contain |
|---|---|---|
| `none` | a yes/no on one proposed time | any enumeration of busy times |
| `free_busy` | intervals busy / free / tentative | reason, category, label, location, participants |
| `category` | `free_busy` + `academic` \| `work` \| `social` \| `personal` | free text of any kind |
| `full` | `category` + a human-readable label | — needs an explicit, logged, scoped grant |

`"busy 2-4pm"` is permitted at `free_busy`. `"therapy at 2pm"` is only ever possible at `full`.
Default for a new negotiation is `free_busy`. Implement the enum exactly; do not reinterpret it.

**The category enum is deliberately blunt.** `personal` absorbs health, therapy and family. Never
add `medical`, `health` or similar — a category that reveals *why* someone is busy defeats the
ladder. **Reasons are a closed vocabulary** (`reason_code`), never prose: free-text explanation
is the most common way a careful system leaks.

### Decisions already made that you must not relitigate

- **Disclosure is enforced server-side, on egress, in one place** (the privacy service). Not in
  agents, not in clients. A client bug must not become a privacy breach.
- **Identity comes from the validated token, never from a client-supplied id**, on every path.
- **Cross-student reads need an explicit grant row and write an audit record.** No implicit sharing.
- **`student_ref` is a per-negotiation pseudonym**, never a name, email or stable id.
- **No MCP anywhere.** Cubbie's sandbox does not support it. The Skill boundary is HTTPS/443.
- **Agent-to-agent traffic never routes through Cubbie** — Cubbie texts only its own student.
- **The negotiation loop is bounded** (`max_rounds`, ceiling 20). Failure to converge is a
  product outcome that escalates to a human, not an error to retry away.
- **Contracts are frozen.** Need a change? Write it in your handoff, set `REVIEW`, and stop.


### Specific to T9

- You are **an untrusted client** like any other (trust boundary B1 in `docs/architecture.md`).
  The backend filters; you render. Never add disclosure logic here.
- A group chat is a **many-to-many** surface: anything posted to the channel is visible to
  everyone in it, including members who are not participants in the negotiation. Check the
  disclosure level against the **channel**, not against the member who asked.
- Reuse the `reason_code` vocabulary when explaining a decline. Never paraphrase it into prose —
  that is precisely where a leak would appear.
- Failure to converge escalates, and is shown honestly in the channel.
- Track 3 is the first track that gets dropped if time runs short
  (`docs/execution-plan.md`). Keep it thin and keep it working.
